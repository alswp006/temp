## 0. 포지셔닝

### 어필하는 것

> **"기록을 나 혼자 하지 않아도 되는 앱"**

식단 기록이 실패하는 이유는 정확도가 아니라 귀찮음이다.
귀찮음을 없애는 방법은 두 가지뿐이다. **입력을 줄이거나, 남이 대신 해주거나.**
이 앱은 둘 다 한다.

| 축 | 내용 |
|---|---|
| 반복 학습 | 자주 먹는 식사는 두 번째부터 1탭. 확정한 끼니는 다시 인식하지 않는다 |
| 대리 기록 | 트레이너·코치·친구가 내 운동과 식단을 대신 써줄 수 있다 |
| 같이 하기 | 멘토-멘티 연결, 그룹 배틀 |
| 알아서 바뀌는 목표 | 체중 추세로 실제 소비량을 역산해 매주 목표 갱신 |

### 어필하지 않는 것 — 급식은 엔진이지 간판이 아니다

식단표 기반 객관식 인식은 여전히 이 앱의 **정확도 엔진**이다. 아키텍처에서 빠지지
않는다. 다만 겉으로 "급식 앱"이라고 내걸지 않는다. 이유는 셋이다.

1. 시장이 좁아 **보인다**. "나는 급식 안 먹는데"에서 설치가 끊긴다
2. 실제로는 급식만의 성질이 아니다. **메뉴가 반복되는 모든 식사**에 같은 원리가
   적용된다 — 구내식당, 학식, 집밥 루틴, 단골 식당, 밀프렙
3. 기존 앱과 겨루는 지점이 "정확도"가 되면 진다. 상대는 DB와 유통이 크다

> 식단표 = "내가 반복하는 식사 목록"의 한 종류.
> 유저에게는 **'내 식사 세트'** 로 보이고, 급식 이용자는 그걸 사진 한 장으로 채울 뿐이다.

`구현` — `MealSet`이 1급 개념이고 (`app/services/mealsets.py`), `Canteen`은 "메뉴가
반복되는 장소"라는 일반 개념입니다. UI 어디에도 "급식"이라는 단어가 없습니다.

### 핵심 가설 (내부용)

> **후보 목록을 알면 사진 인식이 "열린 문제"에서 "객관식"으로 바뀐다.**

AI가 추정할 것은 "무슨 음식인가"가 아니라 **"표준량 대비 얼마나 담았나"** 하나로
줄어든다.

`구현` — `app/vision/prompts.py`, `app/services/recognition.py`.

### 확정된 전제

| 항목 | 결정 |
|---|---|
| 식단표 확보 | **유저가 직접 입력** (급식업체 제휴 없음) |
| 1단계 | 개인용 3개월 |
| 2단계 | 지인 그룹 3개월 (멘토-멘티 + 배틀) |
| 3단계 | 출시 3개월 |
| 과금 주체 | **멘토(코치)가 낸다.** 멘티는 무료로도 쓸 수 있다 |
| 사진 인식 | 상용 비전 모델 API |
| 영양 DB | 식약처 식품영양성분 통합 DB (약 9.2만 건) |

### 단계별로 검증할 것

| 단계 | 검증 질문 | 실패 시 |
|---|---|---|
| 1 | 만든 사람이 3개월 계속 쓰는가 | 여기서 중단. 손실 최소 |
| 2 | 남이 대신 기록해주면 멘티가 남아 있는가 | 개인 도구로 남기고 종료 |
| 3 | 코치가 자기 돈으로 시트를 사는가 | 무료/오픈소스 전환 |

## 1. 공통 아키텍처

### 1.1 기술 스택

| 레이어 | 선택 | 이유 |
|---|---|---|
| 서버 | Python + FastAPI | 익숙한 스택, 비동기 처리 |
| DB | SQLite → PostgreSQL | 1단계는 SQLite, 이후 Postgres. 코드는 동일 |
| 큐 | **jobs 테이블** | Redis 대신. 양쪽 DB에서 동일 동작, 재시작 견딤 |
| 노출 | Cloudflare Tunnel | 공인 IP·포트 개방 불필요 |
| 클라이언트 1단계 | iOS 단축어 + 텔레그램 봇 | 앱 개발 0 |
| 클라이언트 2단계 | PWA + 단축어 병행 | 안드로이드 지인 커버 |
| 비전 | 프로바이더 추상화 | Anthropic / Gemini / stub 교체 가능 |

> 원안의 Redis + RQ 대신 `jobs` 테이블을 썼습니다. 이유는
> [ARCHITECTURE.md §3](ARCHITECTURE.md).

### 1.2 인식 파이프라인

```
사진 수신
  └ 촬영 시각 → 끼니 판정 (조식 05–10 / 중식 11–14 / 석식 17–21 / 그 외 간식)
  └ 소속 식당 + 날짜 + 끼니 → 식단표 조회
       ├ 식단표 있음 → 메뉴 후보 N개를 프롬프트에 주입 (객관식 모드)
       └ 식단표 없음 → 열린 인식 모드 (정확도 낮음을 결과에 표시)
  └ 비전 모델 K회 병렬 호출
  └ 항목별 portion_ratio 중앙값 산출 + 항목 등장 빈도로 신뢰도 계산
  └ 메뉴 → 식약처 food_code 매칭 → 100g당 영양소 × 실제 중량
  └ 개인 보정계수 적용
  └ 저장 → 결과 푸시
```

`구현` — `app/services/recognition.py:analyze_meal()`.

### 1.3 응답 스키마

절대 그램을 물어보지 않는다. **표준 배식량 대비 비율**을 물어본다.

```json
{
  "items": [
    { "menu_id": 41, "portion_ratio": 1.2, "confidence": 0.92 },
    { "menu_id": 43, "portion_ratio": 0.5, "confidence": 0.88 },
    { "menu_id": null, "free_text": "요구르트", "estimated_g": 65, "confidence": 0.40 }
  ],
  "tray_detected": true,
  "notes": ""
}
```

프롬프트 규칙: 후보에 없는 것은 `menu_id: null` + free_text로만 / 안 담은 메뉴는
배열에서 빼되 추측으로 넣지 말 것 / 1.0 = 표준 배식량, 눈대중이면 0.25 단위.

`구현` — `app/vision/prompts.py`. 구조화 출력으로 스키마를 강제합니다.

### 1.4 데이터 모델

`구현` — `app/models.py`. 원안의 테이블이 전부 있고, 다음이 추가됐습니다:
`login_codes` / `api_tokens` (인증), `menu_reports` (오류 신고),
`calibration_samples` (저울 원자료), `jobs`, `notifications`,
`battle_participants`, `daily_scores`.

`category`는 밥 / 국·찌개 / 주찬 / 부찬 / 김치 / 후식 6종으로 고정한다.
`logged_by`와 `audit_logs`가 대리 기록의 핵심이다. **모든 레코드는 "누가 썼는지"를
갖는다.**

### 2.2 F-01 상세 — 식단표 입력

유저 입력 방식이므로 여기가 제일 귀찮은 지점이다. 그래서 **주 1회 30초**로 끝나야
한다. 식단표에 중량·열량이 없으면 표준 배식량 기본값(밥 210g, 국 250g, 주찬 120g,
부찬 60g, 김치 40g)을 적용한다.

`구현` — `nutrition.STANDARD_PORTION_G`.

### 2.3 F-10 상세 — 적응형 목표

```python
trend[d] = 0.1 * raw[d] + 0.9 * trend[d-1]
주간_체중변화 = trend[오늘] - trend[7일전]
평균_섭취 = mean(일별 섭취 kcal, 최근 7일)
추정_TDEE = 평균_섭취 - (주간_체중변화 * 7700 / 7)
# 3주 가중 이동평균 (0.5 / 0.3 / 0.2), 직전 추정 대비 ±15% 클램프
목표_kcal = 추정_TDEE + 목표_조정   # 감량 -400, 유지 0, 증량 +250
목표_단백질_g = 체중_kg * 1.8
```

핵심은 **목표치를 유저가 덮어쓸 수 있어야 한다**는 것.

`구현` — `PUT /targets/current` + `pinned`. 단, 기초대사량 하한은 유저 본인에게도
적용됩니다.

### 2.5 M3 종료 시 판정

| 지표 | 통과 기준 |
|---|---|
| 기록 일수 | 90일 중 70일 이상 |
| 끼니당 소요 시간 | 15초 이하 |
| 수정 발생률 | 30% 이하 |
| 칼로리 오차 (저울 대비) | 평균 ±12% 이내 |

**기록 일수가 50일 미만이면 여기서 끝낸다.** 내가 안 쓰는 걸 남이 쓸 리 없다.

> 수정 발생률은 `/api/reports/weekly`의 `edit_rate`로 바로 측정됩니다.

## 3. Phase 2 — 지인 그룹 (M4–M6)

> **목표: 10~30명 중 절반이 4주 차에도 주 3일 이상 기록한다.**

| ID | 기능 | 구현 |
|---|---|---|
| G-01 | 계정·인증 (비밀번호 없음) | ✅ 매직링크 |
| G-02 | 그룹(식당), 초대 코드 | ✅ |
| G-03 | 메뉴 공동 편집, 오류 신고 | ✅ 2명 이상 동의 시 재확인 |
| G-04 | PWA | ✅ 오프라인 큐 포함 |
| G-05 | 웹 카메라 입력 | ✅ |
| G-06 | **멘토-멘티 연결** | ✅ |
| G-07 | **대리 기록** | ✅ |
| G-08 | **운동 기록** | ✅ 사진/음성/탭 |
| G-09 | 배틀 | ✅ |
| G-10 | 푸시 | ⚠️ 인앱 알림만 |

**G-06·G-07이 이 단계의 진짜 주인공이다.** 멘토-멘티는 소셜 기능이 아니라
**입력 문제의 해법**이다. 지금 PT 받는 사람들은 이미 이걸 카톡으로 하고 있다.
**앱 밖에서 벌어지는 워크플로우를 앱 안으로 가져오는 것**이 제품의 정체다.

### 3.3 멘토-멘티 연결

**권한 모델 (기본값은 전부 off)**

| 범위 | 조회 | 대리 기록 |
|---|---|---|
| 운동 | 선택 | **선택 (기본 권장 on)** |
| 식단 | 선택 | 선택 |
| 체중 | 선택 | **불가 — 본인만 입력** |
| 목표 설정 | 열람 | **제안만 가능.** 멘티 수락 시 반영 |
| 사진 원본 | 선택 | — |

**목표 설정 가드** — 코치가 멘티 목표를 자유롭게 넣게 두지 않는다.

* 목표 칼로리가 추정 기초대사량 아래로 내려가면 저장 자체를 막는다
* 주간 감량 목표가 체중의 1%를 넘으면 경고 + **멘티 본인 확인**
* 목표 변경 이력은 멘티에게 항상 보인다

`구현` — `app/services/permissions.py`, `app/services/targets.py`,
`tests/test_permissions.py`.

### 3.4 대리 기록의 3원칙

1. **표시** — 모든 레코드에 작성자 배지. "코치 김OO가 기록함"
2. **되돌리기** — 멘티는 대리 기록을 언제든 수정·삭제
3. **로그** — 모든 대리 행위는 `audit_logs`에 남고 멘티가 열람 가능

멘토 대시보드는 미기록 3일 이상이면 **카드 색만 바뀐다** (자동 독촉 알림 없음).

### 3.5 운동 기록 — 대리 기록의 주 대상

| 경로 | 방식 | 언제 |
|---|---|---|
| A. 사진 | 수첩·화이트보드·타 앱 화면 1장 → 세트 파싱 | **1순위.** 세션 끝나고 3초 |
| B. 음성 | 한 문장 → 파싱 | 이동 중 |
| C. 탭 | 스테퍼 | 정밀 수정용 |

소모 칼로리는 MET로 계산하되 **적응형 TDEE에는 넣지 않는다.** 체중 추세에서
역산한 소비량에 이미 운동이 포함돼 있어 이중 계산이 된다.

`구현` — `app/services/workouts.py`. B는 로컬 규칙 파서를 먼저 시도합니다.

### 3.6 배틀 설계

경쟁 요소는 넣되, **점수에서 체중은 완전히 뺀다.**

| 항목 | 점수 |
|---|---|
| 끼니 기록 | 끼니당 2점 (하루 최대 6점) |
| 운동 기록 | 3점 (본인 입력·코치 대리 동일) |
| 체중 기록 | 1점 |
| 목표 칼로리 ±10% 이내 | 3점 |
| 단백질 목표 달성 | 2점 |
| 메뉴표 등록 (그 주 최초) | 5점 (1회) |

체중 절대값은 **비공개 고정** (설정으로도 못 켬). 패배자 벌칙·랭킹 강등·연속 실패
알림은 넣지 않는다.

`구현` — `app/services/scoring.py`, `tests/test_battles.py`.

### 3.8 M6 종료 시 판정

| 지표 | 통과 기준 |
|---|---|
| 4주 차 잔존율 | 50% 이상 |
| **멘티 잔존율 vs 단독 유저 잔존율** | **멘티 쪽이 1.5배 이상 높을 것** |
| 대리 운동 기록 | 코치가 주 3회 이상 대신 입력 |
| 메뉴표 자발적 등록 | 내가 아닌 사람이 최소 1회 |
| 유저당 월 AI 비용 | 1,500원 이하 |

**두 번째 지표가 제일 중요하다.** 멘토가 붙은 사람이 더 오래 남지 않는다면
멘토-멘티는 그냥 기능 하나일 뿐이고, 포지셔닝을 다시 짜야 한다.

## 4. Phase 3 — 출시 (M7–M9)

> **목표: 모르는 사람 100명이 설치하고, 그중 5명 이상이 결제한다.**

### 4.1 비용 구조 전환

```
같은 canteen + date + meal_type 안에서는 메뉴 후보가 동일하다
첫 번째 유저:  K=5 → "그날 그 식당의 기준 해석" 저장
이후 유저:     K=1 → 기준과 대조. 불일치 시 K=3 추가 후 기준 갱신
```

같은 식당 유저가 많을수록 **1인당 단가가 내려간다.** 확산 인센티브와 비용 구조가
같은 방향을 본다.

`구현` — **이미 들어가 있습니다.** `RecognitionBaseline` + `CallPolicy`.
나중에 마이그레이션하는 것보다 지금 넣는 게 쌉니다.

### 4.2 요금제 — 개인 구독에서 코치 시트로

| 플랜 | 대상 | 내용 | 가격 |
|---|---|---|---|
| 무료 | 개인 | 사진 기록 하루 2회, 메뉴표 무제한, 배틀, 멘토 1명 | 0원 |
| 플러스 | 개인 | 무제한 기록, 적응형 목표, 주간 리포트, CSV | 월 3,900원 |
| **코치** | 트레이너 | 멘티 10명, 대시보드, 대리 기록, 멘티 전원 플러스 포함 | 월 19,900원 |
| 코치 프로 | 다회원 | 멘티 30명, 그룹 리포트 | 월 49,000원 |

개인이 다이어트 앱에 3,900원 내는 건 망설이지만, 트레이너에게 19,900원은
**사업 도구 비용**이다. 트레이너 1명이 회원 10명을 데려오니 획득 비용도 사실상 0.

메뉴표 등록은 전 플랜 무료로 연다. 그게 제품의 연료다.

`구현` — 멘티 한도(`PEER=2 / COACH=10 / COACH_PRO=30`)는 강제되고 있습니다.
결제 연동은 없습니다.

### 4.5 M9 종료 시 판정

| 지표 | 통과 기준 |
|---|---|
| 유료 코치 | 10명 이상 |
| 코치당 활성 멘티 | 평균 5명 이상 |
| 멘티 7일 잔존율 | 40% 이상 |
| **코치 2개월 차 갱신율** | **70% 이상** |
| 유저당 원가 | 매출의 40% 이하 |

**코치 갱신율이 진짜 신호다.** 두 번째 달에도 결제하면 회원 관리에 실제로 쓰고
있다는 뜻이다.
