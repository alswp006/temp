# 아키텍처

왜 이렇게 만들었는지에 대한 문서입니다. 무엇이 있는지는 코드가 말해주고,
이 문서는 **왜 그 선택이었는지**만 다룹니다.

---

## 1. 핵심 가설과 그 구현

> **후보 목록을 알면 사진 인식이 "열린 문제"에서 "객관식"으로 바뀐다.**

일반 앱은 세상 모든 음식을 상대해야 합니다. 이 앱은 그날 후보 5~6개만 상대합니다.
AI가 추정할 것은 "무슨 음식인가"가 아니라 **"표준량 대비 얼마나 담았나"** 하나로
줄어듭니다.

이 가설이 코드에 나타나는 지점은 세 곳입니다.

**(1) 프롬프트가 그램을 묻지 않습니다.** `app/vision/prompts.py`의 응답 스키마는
`portion_ratio`(표준 배식량 대비 비율)를 요구하고, 후보에 없는 음식에만
`estimated_g`를 허용합니다. 모델은 "약 1.2배 담겼다"를 "252그램"보다 훨씬 잘합니다.
그램은 우리가 통제하는 산수로 나옵니다.

```
final_g = menu_item.standard_g × portion_ratio × calibration[category]
```

**(2) 후보 목록은 요청마다 바뀌므로 유저 턴에 들어갑니다.** 시스템 프롬프트는 고정
문자열이고 캐시 브레이크포인트를 답니다. 앞부분이 한 바이트라도 바뀌면 캐시가
깨지므로, 변하는 것은 전부 뒤로 보냅니다.

**(3) 구조화 출력을 강제합니다.** JSON을 정중히 부탁하고 정규식으로 긁어내는 대신
`output_config.format`으로 스키마를 강제합니다. 파싱 실패 재시도 루프가 통째로
사라집니다.

식단표가 없으면 열린 인식 모드로 떨어지되, `Meal.open_mode` 플래그가 서고 UI에
"식단표 없음 — 오차 큼"이 표시됩니다. 정확도를 조용히 낮추지 않습니다.

## 2. K는 상수가 아니다 — 비용 구조

Phase 1·2의 "5회 호출 중앙값"은 개인용 사치입니다. 그대로 출시하면 적자입니다.
그래서 캐시 아키텍처를 **처음부터** 넣었습니다. 나중에 얹는 것보다 지금 넣는 게
싸기 때문입니다.

```
같은 canteen + date + meal_type 안에서는 메뉴 후보가 동일하다
   → 인식 결과를 공유할 수 있다

첫 번째 유저:  K=5 호출 → "그날 그 식당의 기준 해석"으로 저장
이후 유저:     K=1 호출 → 기준 해석과 대조
               일치   → 그대로 사용        (cache_hit = true)
               불일치 → K=3 추가 후 기준 갱신 (cache_hit = false)
```

`RecognitionBaseline` 행은 (식당, 날짜, 끼니, 메뉴항목)마다 하나씩, 표준량 비율의
러닝 평균과 등장률을 들고 있습니다. `CallPolicy.disagrees()`가 두 가지를 봅니다.

* 어떤 항목의 비율이 허용 오차(기본 0.35)를 넘게 벗어남
* 기준이 "거의 항상 있다"(등장률 ≥ 0.8)고 하는 항목을 이번 판독이 통째로 놓침

**중앙값을 쓰는 이유**: K=5에서 한 번의 호출이 반 국자를 두 국자로 잘못 봐도 답이
끌려가지 않습니다. 평균이면 끌려갑니다. K≥3에서는 절반 미만의 호출만 본 항목을
버리는데, 이건 "한 번 헛본 것"과 "실제로 있는데 가려진 것"을 구분하는 가장 싼
방법입니다. K=1에서는 합의를 잴 수 없으므로 전부 유지합니다.

효과: 20명 규모 식당 기준 호출량 60~70% 절감이 목표이고, `/api/reports/weekly`의
`cache_hit_rate`가 실제 값을 보여줍니다.

## 3. 왜 잡 큐가 테이블인가

Redis/RQ 대신 `jobs` 테이블입니다.

* SQLite와 PostgreSQL에서 **동일하게** 동작합니다. Phase 1은 노트북 SQLite,
  Phase 2는 Postgres인데 코드가 바뀌지 않습니다.
* 재시작을 견딥니다. 분석 도중 죽어도 사진이 사라지지 않습니다.
* 인프라가 하나 줄어듭니다. 혼자 만드는 속도가 최대 리스크인 프로젝트에서
  운영 컴포넌트 하나는 비쌉니다.

클레임은 `UPDATE ... WHERE id IN (...) AND status='queued'`로 원자적입니다.
SQLite에 `SKIP LOCKED`가 없어서 그렇게 했고, 덕분에 워커를 여러 개 띄워도 안전합니다.
실패는 5s → 30s → 2m → 10m 백오프로 재시도하고, 죽은 워커가 잡은 일감은
`reclaim_stale()`이 되돌립니다.

**핸들러의 트랜잭션은 실패 시 롤백됩니다.** 반쯤 쓰인 항목이 남으면 안 되기
때문입니다. 그래서 "이 식사는 실패했다"는 표시는 **별도 세션**에서 씁니다 —
그것도 원래 세션을 먼저 롤백한 뒤에요. 안 그러면 자기 자신이 잡고 있는 행 잠금에
걸려 데드락이 납니다. (`app/jobs/handlers.py`의 주석 참조.)

## 4. 데이터 모델의 두 불변식

**모든 유저 소유 레코드는 `logged_by`를 가집니다.** 코치가 멘티의 운동을 쓰는 것은
예외 상황이 아니라 1급 시나리오입니다. UI가 "코치 김OO가 기록함"이라고 말할 수
있어야 하고, 그러려면 스키마가 그걸 알아야 합니다.

**모든 제3자 쓰기는 감사 로그를 남깁니다.** 자기 자신의 행위는 남기지 않습니다 —
로그의 존재 이유가 "누가 내 기록을 건드렸나"인데 본인 수정으로 채우면 답이
묻힙니다.

### 굳이 커스텀 타입 두 개를 만든 이유

`UTCDateTime`과 `EnumStr`은 편의가 아니라 **런타임 폭탄 제거**입니다.

* Postgres는 `timestamptz`로 aware datetime을 돌려주지만 SQLite는 naive를 돌려줍니다.
  둘을 비교하면 `TypeError`가 나는데, 하필 그걸 비교하는 코드 경로에서만 납니다.
  경계에서 정규화하는 게 훨씬 쌉니다.
* `Mapped[FoodCategory]`에 `String` 컬럼을 쓰면 쓰기는 되지만 **읽으면 평범한 str**이
  돌아옵니다. `.value`가 터지고 `is FoodCategory.RICE`가 조용히 False가 됩니다.
  실제로 이 프로젝트에서 한 번 터졌고, 그래서 타입 레벨에서 고쳤습니다.

`sqlalchemy.Enum`을 쓰지 않은 것은 의도적입니다. 네이티브 DB enum이 없어야 멤버
추가가 마이그레이션이 아니라 코드 변경으로 끝납니다.

## 5. 권한 모델

스코프는 7개이고, 기본값은 **전부 off**입니다.

```
diet:read     diet:write
workout:read  workout:write
weight:read   (weight:write 는 존재하지 않음)
photo:read    goal:propose
```

`weight:write`가 없는 것이 설계입니다. 열거형에 없으므로 부여할 문법 자체가 없고,
`POST /api/weights`는 `user_id` 파라미터를 받지 않습니다. **구성할 수 있는 요청이
없습니다.** `require_self_for_weight()`가 명시적으로도 거절하고,
`tests/test_permissions.py::test_there_is_no_way_to_write_someone_elses_weight`가
모든 스코프를 켠 코치로도 뚫리지 않음을 검증합니다.

`photo:read`가 `diet:read`와 분리된 이유: 사진에는 타인 얼굴·명찰·장소 맥락이
찍힙니다. 칼로리 숫자를 공유하는 것과 원본 사진을 공유하는 것은 다른 결정입니다.

**초대 흐름은 멘티 우선입니다.** 멘토가 링크를 만들지만, 멘티는 수락 **전에**
`GET /api/mentorships/invite/{code}`로 무엇을 요구받는지 전부 봅니다. 이 엔드포인트는
인증이 필요 없습니다 — 무엇을 요구받는지 보려고 먼저 로그인해야 한다면 동의의
순서가 거꾸로입니다.

## 6. 목표 설정의 안전장치

적응형 TDEE는 체중 추세에서 실제 소비량을 역산합니다.

```
trend[d]   = 0.1 × raw[d] + 0.9 × trend[d-1]
주간변화    = trend[오늘] - trend[7일전]
추정 TDEE  = 평균섭취 - (주간변화 × 7700 / 7)
            → 3주 가중이동평균 (0.5 / 0.3 / 0.2)
            → 직전 추정 대비 ±15% 클램프
목표        = 추정 TDEE + 목표조정 (감량 -400 / 유지 0 / 증량 +250)
```

클램프가 필요한 이유: 수분 변화나 하루 기록 누락 같은 한 주의 잡음이 다음 주 목표를
수백 kcal 흔들면 안 됩니다.

가드는 두 개이고 **순서가 중요**합니다.

1. **하드 플로어** — 기초대사량(Mifflin–St Jeor) 아래는 저장 자체가 거부됩니다.
2. **소프트 캡** — 주간 감량이 체중의 1%를 넘으면 저장은 되지만 본인 확인을 받습니다.

테스트를 쓰다가 발견한 것: 70kg인 사람에게는 1%/주를 넘는 목표가 이미 기초대사량
아래라서, 하드 플로어가 먼저 걸립니다. 소프트 캡이 단독으로 발동하려면 더 무거운
몸이어야 합니다. 두 가드가 올바르게 겹쳐 있다는 뜻이고,
`test_bmr_floor_fires_before_the_rate_cap_for_a_light_body`가 이 상호작용을
문서화합니다.

**운동 소모 칼로리는 여기에 안 들어갑니다.** 체중 추세 역산에 이미 운동이
포함돼 있습니다. 더하면 이중 계산이 되고, 가장 열심히 훈련하는 사람의 칼로리
목표만 부풀립니다.

## 7. 프런트엔드에 빌드 스텝이 없는 이유

PWA는 순수 ES 모듈 + CSS 토큰입니다. 프레임워크도 번들러도 없습니다.

화면이 일곱 개고 상태가 얕습니다. 빌드 스텝은 여기서 얻는 것보다 드는 게 큽니다 —
설치해야 할 툴체인, 잠긴 의존성, 캐시 무효화, "왜 dev에서만 되지" 부류의 시간.
`web/`을 그대로 서빙하면 끝이고, 서비스 워커가 셸을 캐시합니다.

**오프라인 업로드 큐가 진짜 기능인 이유**: 이 앱 최악의 순간은 신호 한 칸짜리
생활관 지하에서 사진을 찍었는데 그게 날아가는 것입니다. 사진은 IndexedDB에
먼저 들어가고 연결이 돌아오면 비워집니다. 셔터가 연결 상태에 의존하지 않습니다.
4xx는 재시도해도 영영 성공하지 않으므로 큐에서 버립니다 — 안 그러면 영구히
막힌 요청 하나가 뒤를 전부 세웁니다.

## 8. 비전 프로바이더가 세 개인 이유

```python
class VisionProvider(ABC):
    async def analyze_tray(req)       -> TrayAnalysis
    async def parse_menu_board(req)   -> MenuBoardParse
    async def parse_workout_note(req) -> WorkoutParse
```

* **anthropic** — 공식 SDK, 구조화 출력, `effort: low`(후보 목록이 주어진 판독은
  추론 부하가 낮은데 끼니마다 도는 비용 지점입니다), `stop_reason == "refusal"` 처리.
* **gemini** — REST. 스키마가 JSON Schema가 아니라 OpenAPI 서브셋이라
  `to_gemini_schema()`가 변환합니다. 스키마 원본은 하나로 유지됩니다.
* **stub** — 사진 바이트 해시로 결정론적 답을 만듭니다.

`stub`이 장난감이 아닌 이유: **키 없이, 네트워크 없이 전체 시스템이 돕니다.**
CI가 이걸로 파이프라인·집계·캐시·API를 전부 검증합니다. 호출별 `nonce`가 약간의
변동을 주입해서 중앙값 집계 경로까지 실제로 실행됩니다.

프로바이더 초기화가 실패해도(키 누락 등) 앱은 뜹니다. 로그를 남기고 stub으로
떨어지며, 수동 입력·식사 세트·코치 대시보드는 그대로 동작합니다. 키 하나 때문에
앱 전체가 죽지 않습니다.

## 9. 성능상 알아둘 것

* `nutrition.match_food()`는 유사도 함수를 돌리기 전에 2글자 윈도 substring으로
  후보를 좁힙니다. 식약처 DB 9.2만 행을 매 항목마다 파이썬 유사도로 훑을 수는
  없습니다. 정확 일치와 별칭 일치는 그 전에 단락(short-circuit)됩니다.
* `Meal.items` / `Workout.sets` / `MenuPlan.items`는 `lazy="selectin"`이고,
  직렬화 지점에서 `await db.refresh(obj, [...])`를 명시적으로 부릅니다.
  Pydantic의 `from_attributes`가 async 컨텍스트 밖에서 관계를 건드리면
  `MissingGreenlet`으로 터집니다.
* K회 호출은 `asyncio.gather(..., return_exceptions=True)`입니다. 5회 중 1회
  실패는 추정치를 약간 나쁘게 할 뿐 식사를 잃지 않습니다. 전멸일 때만 예외입니다.
